# Campaign Ledger

An independent marketing operations prototype by **Marina Avetisian**, built through AI-assisted development. It demonstrates how fictional advertising and store records become validated SQL reports, audience previews, and a review brief.

**[Open the live demo](https://campaign-ledger.maravetis.chatgpt.site)**

The live demo replays results generated by the working Python pipeline. It does not connect to an advertising account, use company data, or run an LLM in the browser.

## What works

- Python adapters retrieve three separate simulated HTTP sources, with bounded retries.
- Validation checks source freshness against a fixed sample clock, snapshot completeness, dates, record relationships, and refund amounts.
- Transactional SQLite imports preserve the last valid snapshot when an update fails. Corrected snapshots replace earlier records without duplication.
- SQL calculates campaign spending, customer acquisition cost, attributed order revenue, refunds, and ROAS. Sources are aggregated before joining to avoid multiplying totals.
- The dashboard provides campaign filters, source status, import history, audience previews, CSV exports, threshold alerts, and rules-based review briefs.
- An optional Claude API adapter checks returned campaign references and numeric facts and falls back on invalid or unavailable responses. Tests use simulated model responses; no live model connection has been verified.

## Run the demo locally

Requirements: **Python 3.10+** and **Node.js 18+**. The project uses their standard libraries; no package installation is required. Run these commands from the repository root:

```sh
python3 campaign-ledger-site/build_scenarios.py
python3 campaign-ledger-site/build_site.py
node campaign-ledger-site/check_dashboard.cjs
```

Open `campaign-ledger-site/dist/index.html` in a browser. Select **Successful refresh**, **Google source fails**, or **Corrected spend & refund**, then click **Run sample workflow** to explore the generated result.

`build_scenarios.py` actually exercises the HTTP adapters and SQLite pipeline using temporary localhost servers and an in-memory database. The browser controls replay those outcomes; they do not execute Python.

## Inspect the persistent workflow

In one terminal:

```sh
cd campaign-ledger
python3 mock_sources.py --scenario success --port 8765
```

In another terminal, from the repository root:

```sh
cd campaign-ledger
python3 workflow.py --base-url http://127.0.0.1:8765
```

Results are written to `campaign-ledger/output/workflow.json` and a local SQLite database. Stop and restart the mock source server with `--scenario failure` or `--scenario correction`, then rerun the workflow. Failure returns a nonzero exit status and preserves the earlier report; a corrected snapshot updates the values. Repeating the import leaves the calculated metrics unchanged.

The reference clock is **October 3, 2026, 09:00 UTC** and records cover September 19–October 2, 2026. Dates are part of a reproducible fictional fixture, not today's data.

## Tests

```sh
cd campaign-ledger
python3 -m unittest -v test_report.py test_workflow.py
```

The 14 backend tests cover aggregation, metric denominators, duplicate imports, transaction rollback, source failures, corrections, stale/incomplete snapshots, refund validation, and the optional model adapter's validation/fallback. The dashboard script check exercises scenario controls, filters, tabs, exports, briefs, and calculator validation against a minimal DOM; it is not browser layout testing.

The original CSV-only reporting path is also available:

```sh
cd campaign-ledger
python3 build_report.py
node test_dashboard.cjs
```

## Definitions and limitations

**CAC** = advertising spend plus sample allocated acquisition costs, divided by new customers in the reporting window. **Net ROAS** = attributed order revenue minus refunds recorded in that window, divided by advertising spend. Refunds follow refund dates; this is not an order-cohort return rate. These metrics do not calculate profit.

All sample money is USD, stored as integer cents. Each customer and order has one assigned campaign; overlapping platform attribution is not modeled. Zero denominators are reported as unavailable. The revenue LTV calculator uses adjustable assumptions, not a prediction learned from the short sample history.

The sources are **mock contracts**, not implementations of the official Meta or Google APIs. Live authentication, pagination, attribution reconciliation, multi-currency processing, scheduling, low-code orchestration, hosted persistence, and automatic campaign actions are not implemented. The prototype demonstrates complete-snapshot imports, not incremental webhook processing.

To enable the optional local Claude tool, provide `ANTHROPIC_API_KEY` and `ANTHROPIC_MODEL` as server-side environment variables and add `--claude` to the workflow command. No credentials are included. Its output requires human review; it is not an autonomous advertising agent.

Metric references: [Shopify CAC](https://www.shopify.com/blog/ecommerce-customer-acquisition), [Shopify ROAS](https://www.shopify.com/blog/roas), [Shopify LTV](https://www.shopify.com/blog/customer-lifetime-value-analysis).
